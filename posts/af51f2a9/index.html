重构类路径：pickle 缓存集体失效

服务重构把类移到新模块后，旧 pickle 缓存反序列化报 AttributeError，缓存命中的请求批量 500；改用带版本前缀的 JSON 缓存并双读双写过渡后恢复。

问题背景

推荐服务用 Python 编写，gunicorn 多 worker 部署，特征向量直接缓存在 Redis 里：pickle.dumps(obj) 存成 bytes，key 是 feat:{user_id}，TTL 24 小时，命中率长期在 30% 到 40% 之间。

上周做了一次代码结构整理：把 app/models/feature.py 拆到 app/features/vector.py，类 Feature 顺便重命名为 FeatureVector，旧模块删除。重构本身通过了单元测试，本地跑、CI 跑都是绿的，评审时大家关注的是新目录结构是否清晰，没有人想到缓存里还躺着几十万个旧对象。

故障现象

灰度第一台实例上线不到十分钟，错误率冲到 30% 左右，全是 500。日志堆栈集中在 pickle.loads：AttributeError: Can't get attribute 'Feature' on <module 'app.models.feature'>。

规律很明显：缓存命中的请求全部失败，未命中的请求正常——因为未命中会回源计算并写入新缓存。把该实例对应的缓存 flush 掉，服务立刻恢复，但数据库 QPS 从 2k 飙到 12k，差点把库打挂。回滚代码也能恢复。

继续滚动发布后问题更清楚：新实例读旧缓存报错，旧实例读新实例写入的缓存也报错，两个版本互相不认。发布窗口里，服务实际上处于「一半缓存不可用」的状态。

排查过程

第一步确认错误分布：只有缓存命中的请求 500，未命中的正常，问题在「读缓存」而不是业务逻辑。

第二步看堆栈和变更记录：pickle.loads 失败，找不到旧类；git log 确认类已移动并重命名。为了让证据更硬，本地做了双向复现——旧代码 dumps，新代码 loads 报 AttributeError；新代码 dumps，旧代码 loads 同样失败。

第三步拆开看缓存字节。用 pickletools.dis 打印 pickle 的指令序列，能清楚看到 GLOBAL 操作码里写着 app.models.feature 和 Feature——pickle 保存的不是「字段快照」，而是「模块路径 + 类名」的全局引用。反序列化时它按名字去 import 模块、找类，模块没了或类改名了，数据就再也打不开。

第四步评估影响面：TTL 24 小时、命中率 30% 以上、滚动发布 10 台实例，意味着新实例一启动就会踩到旧缓存；而全量 flush 会造成缓存击穿，数据库扛不住。这解释了为什么「flush 能恢复但不能这么干」。

第五步排除其他可能：Redis 连接正常、其他 key 读写正常、bytes 完整、镜像一致，排除了基础设施与编码问题。

最后复盘设计：缓存 key 没有版本号，value 也没有 schema 版本，新旧格式无法区分，发布过程没有任何灰度切换的抓手。缓存格式一直被当成「内部实现」，实际上它是跨版本的隐式契约。

解决方案

  1. 止血：换 key 前缀。新代码只读写 feat:v2:{user_id}，旧 key 靠 TTL 自然过期，不做 FLUSHALL，避免击穿数据库。
  2. 双读双写过渡。新实例先读 v2，未命中回源计算并写 v2；灰度期间旧实例继续用 v1，两套缓存互不干扰；全量切换后旧 key 自然淘汰。
  3. 根治：换序列化格式。缓存值改为 JSON（或 msgpack）加显式 schema，用 Pydantic 模型定义字段并带 schema_version；字段增减走兼容解析，缺省值兜底、未知字段忽略，不再持久化 Python 对象。
  4. 过渡兼容。如果短期内必须继续读旧 pickle，自定义 Unpickler 重写 find_class，把旧模块路径映射到新路径；同时保留旧模块的 re-export 兼容层。这只是过渡手段，不能长期依赖。
  5. 击穿保护。缓存失效用按前缀 SCAN + 批量 DEL；回源加 singleflight 互斥与限流，必要时先跑预热任务。
  6. 验证。灰度 10% 实例读旧缓存零错误；全量后命中率回到 35%；模拟缓存全失效时数据库 QPS 控制在 6k 以内；新老版本并存 24 小时无 500。

根因分析

pickle 序列化的是「对象图 + 全局引用」，保存模块路径与类名，不是自描述的数据结构。代码结构一变——模块移动、类重命名、模块删除——旧数据就失去可解析性。它没有字段名与类型的稳定契约，兼容性完全依赖代码结构不变。

缓存 TTL 24 小时与滚动发布叠加，意味着「跨版本共存」是常态。缓存格式实际上是接口契约，但团队把它当成了实现细节，既没有版本号，也没有灰度切换方案。

还有一个容易被低估的点：pickle 反序列化可以执行任意代码，缓存一旦被污染就是 RCE 入口。把 pickle 用于缓存、队列这类半信任数据，本身就是安全负债。

监控也有盲区：只盯命中率和错误率，没有「反序列化失败」这个维度，问题先在用户侧的 500 上暴露，而不是在监控大盘上。

预防措施

  • 序列化规范：跨版本、跨进程边界的数据一律用 JSON、msgpack 或 protobuf，配显式 schema 与版本号；pickle 只用于进程内临时对象。
  • 缓存 key 规范：采用 业务:实体:v{schema_version}:id 结构，升级即换前缀，旧数据靠 TTL 淘汰，禁止把全量 FLUSH 当常规手段。
  • 发布检查单：类移动、重命名、字段变更时，必须检查缓存、队列、会话等持久化格式的兼容性，并在灰度阶段验证双版本共存。
  • 失效与击穿：前缀失效 + 预热 + singleflight；批量失效前先压测回源能力。
  • 监控补齐：反序列化失败计数、缓存命中率、回源 QPS 三条曲线一起看；错误日志按异常类型聚合。
  • 安全底线：永不反序列化不可信来源的 pickle；缓存和队列加访问控制，敏感场景考虑签名校验。
  • 文档化契约：把缓存格式、schema 版本与兼容窗口写进接口文档，标明哪些字段可增删、哪些变更需要换前缀，避免下次重构再把它当内部实现随手改。

总结

pickle 很方便，但它保存的是「你的代码长什么样」，而不是「数据本身长什么样」。代码一重构，旧缓存就全部作废——不是缓存坏了，是契约变了却没有版本。

把缓存当接口来设计：有 schema、有版本、有灰度、有回退。这样下次重构时，缓存只会慢慢过期，而不会在发布瞬间把三成请求打成 500。
