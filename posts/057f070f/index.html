多进程各自轮转：日志每天丢一段

8 个 gunicorn worker 各自用 TimedRotatingFileHandler 轮转同一文件，午夜互踩，部分进程继续写旧 inode，日志每天断档；改单写者后恢复。

问题背景

订单服务的 Python 应用用 gunicorn 部署，8 个 worker，preload_app=True。日志配置在应用启动时初始化：TimedRotatingFileHandler 写 /data/logs/app/app.log，每天午夜轮转，保留 30 天，按天归档。

这套配置从项目第一天就在用，日志看起来一直在写，运维也习惯了每天去翻 app.log.2026-xx-xx。直到一次线上问题复盘，需要查凌晨的一段调用链，才发现日志对不上：关键五分钟的记录直接缺失了。

故障现象

把最近两周的日志文件按天对齐，问题很规律：每天 00:00 到 00:05 左右都有断档，少的几十行、多的上千行；app.log 当天的大小明显偏小；与此同时，前一天的归档文件在次日凌晨还在增长，mtime 一直往后跳。

更奇怪的是权限：有几天的归档文件属主是 root，日志采集器读不了，只能靠人工补权限。还出现过一小段日志在两个文件里各有一半的情况，像是被「劈开」了。

应用本身没有报错，gunicorn worker 也没有重启，监控上 CPU、内存都正常。日志问题就这样安静地存在了很久，直到有人真的需要它。当时还怀疑过日志采集器的过滤规则，核对配置后发现过滤条件没变，问题在文件本身。

排查过程

第一步看文件 inode。ls -li 发现当天的 app.log 和几个 worker 打开的文件描述符指向的 inode 不一致；lsof -p <worker_pid> 进一步确认，有的 worker 还在写前一天归档文件的 inode。也就是说，轮转发生后，部分进程没有跟着切换文件，继续往旧文件里写。

第二步看轮转实现。日志配置在主进程加载应用时初始化，preload_app=True 让 8 个 worker 通过 fork 继承了同一批文件描述符和 handler 对象。TimedRotatingFileHandler 的轮转是「每个进程各自判断时间、各自 rename、各自重新打开」，进程之间没有任何互斥。

第三步还原午夜那一刻的竞争：第一个进程把 app.log 重命名为归档文件并创建新文件；第二个进程的 handler 还拿着旧 inode 的 fd，继续写归档文件；等它自己触发轮转时，又会去 rename 当前路径上的新文件，导致归档被覆盖或错位。权限问题也来自这里——重新创建文件的进程用户不同，属主就变了。

第四步做复现。本地起 4 个进程，共用同一份 handler 配置写同一个文件，跨过轮转点后统计行数：发送 10 万行，只有 6 万多行落盘，且归档文件在轮转后仍在增长。复现稳定，与线上现象一致。

第五步确认这不是磁盘或采集器的问题：磁盘 IO 正常、inode 充足、采集器配置未变；问题只在「多进程 + 应用内轮转」组合下出现。

解决方案

  1. 改成单写者：应用内引入 QueueHandler + QueueListener，所有 worker 只把日志记录放进队列，由一个监听进程（或主进程里的单线程）负责写文件和轮转。写与轮转只有一个执行者，竞争消失。
  2. 或者交给平台：应用只输出到 stdout，由 systemd/journald 或容器运行时统一收集与轮转。这是 12-Factor 的推荐做法，应用不再关心文件生命周期。
  3. 拆分 worker 文件（折中）：每个 worker 写 app-{pid}.log，轮转与清理交给外部统一任务；文件之间互不干扰，代价是排查时要聚合。
  4. 权限统一：统一运行用户与 umask，轮转后新文件权限保持一致；容器场景确认挂载目录属主。
  5. 验证：8 worker 压测跨午夜，发送 20 万条日志，轮转前后行数守恒、一条不丢；归档文件轮转后不再增长；属主与权限一致；连续观察一周无断档。

根因分析

Python 的 logging handler 是进程内对象，TimedRotatingFileHandler 的轮转逻辑只处理「自己这个进程」的文件流。它假设写入者是单一的——这是设计前提，不是 bug。

多进程场景打破了这个前提：每个 worker 都有一份 handler、各自判断轮转时间、各自执行 rename 与重新打开。rename 是路径操作，多个进程同时做会互相覆盖；已经打开的 fd 指向 inode 而不是路径，进程不主动关闭就不会跟着切换。fork 继承让问题更隐蔽——父子进程共享同一批 fd，谁先轮转谁「赢」，其余的继续写旧文件。

preload_app=True 放大了这一点：handler 在 fork 之前就创建好了，8 个 worker 从出生起就共享同一套文件描述符。如果日志在 fork 之后各自初始化，表现会不同，但只要「多进程写同一文件 + 各自轮转」，竞争依然存在。

预防措施

  • 日志架构规范：多进程应用禁止用应用内轮转直接写共享文件；默认走 stdout + 平台收集，或 QueueListener 单写者模式。
  • 配置审查：代码评审时检查 TimedRotatingFileHandler、RotatingFileHandler 的使用场景，确认写入者唯一。
  • 权限基线：统一服务运行用户与日志目录权限，轮转创建文件后校验属主，采集器读取权限纳入部署检查。
  • 完整性监控：每日统计日志行数与关键心跳日志，出现断档或归档文件异常增长即告警；不要等排障时才发现日志没了。
  • 轮转演练：发布检查里加一条「跨轮转点压测」，验证行数守恒、文件切换正确。
  • fork 意识：涉及 fork 的部署方式（gunicorn preload、multiprocessing）要明确哪些资源在 fork 前初始化，避免共享 fd 的隐蔽继承。

总结

日志轮转看起来是「到点改个名」的小事，但它是有状态的写操作。单进程时它是安全的，多进程时它变成一场没有裁判的竞争——谁先 rename 谁赢，输的进程继续往旧文件里写，日志就这样丢了。

判断标准很简单：同一个文件，是否只有一个进程负责写和轮转？答案是否，就迟早会丢日志。把写入者收敛成一个，问题从根上消失。
