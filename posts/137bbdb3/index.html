双 WAN 会话漂移：长连接被反复重置

双 WAN 按连接哈希负载均衡，健康检查抖动触发频繁切换，会议与网银的长连接因源 IP 变化被重置；按业务固定出口、加会话保持与切换迟滞后稳定。

问题背景

公司出口有两条宽带：电信 500M 做主用，联通 300M 做备份，路由器上配置了双 WAN 负载均衡，按连接哈希把流量分摊到两条线上。日常上网、下载、视频都没问题，出口带宽也确实叠加出了效果。

但「用着用着断一下」的抱怨一直存在：视频会议中途掉线几秒自动重连、网银操作到一半要求重新登录、远程桌面突然断开。每次断的时间都很短，重连后一切正常，单看两条宽带的监控——在线、延迟正常、丢包接近零——找不到任何问题。

故障现象

断连集中在工作日上午和下午的高峰时段，没有固定规律；同一时刻，有人掉线、有人正常。用有线还是无线都会遇到，排除 Wi-Fi 因素；两条宽带各自测速、ping 外网都正常，运营商侧也没有故障记录。

最典型的是视频会议：画面卡住两三秒，然后自动恢复，会议软件日志里能看到「媒体连接重建」；网银更明显，页面直接跳回登录页；远程桌面则是整个会话断开，需要重新连接。这三类应用的共同点是：都是长连接，且服务端对客户端源地址比较敏感。

排查过程

先在路由器上抓包，同时抓两条 WAN 出口。故障时段能看到同一个客户端发起的连接，先走电信出口，几秒后新建的连接改走联通出口，出口公网 IP 随之变化。也就是说，会话在两条线之间「漂移」了。

再查负载均衡策略：按「源/目的 IP + 端口」做连接哈希。这种策略保证单条连接稳定走一条线，但新连接会被重新分配；一旦某条链路被判定故障，后续连接全部切到另一条线，源 IP 立刻变化。

继续查为什么切换这么频繁。健康检查配置是每秒探测一次、连续三次失败判定链路故障、连续三次成功恢复。办公网高峰期，电信线路偶发 1% 到 2% 的丢包，三次探测连续失败的概率不低，链路状态就在 up/down 之间反复抖动；每抖动一次，就触发一轮会话迁移。路由器日志里能看到大量链路状态翻转记录。

然后看会话表：链路被判定故障时，该出口的 NAT 会话被清除；正在传输的 TCP/UDP 会话失去映射，服务端看到的就是连接中断。对视频会议这类 UDP 媒体流，NAT 映射失效等于媒体通道重建；对网银这类做了源 IP 绑定的 HTTPS 会话，源地址一变就要求重新认证。

做对照实验：把视频会议和远程桌面的目标地址固定走电信出口（策略路由），连续观察一周，这两类业务零断连；普通上网和下载仍然双线负载，偶发断连不再影响关键业务。再把健康检查改成连续五次失败才切换、恢复后稳定三十秒才回切，链路翻转次数下降了一个数量级。

解决方案

  1. 按业务分级：视频会议、远程桌面、网银、VPN 这类对源 IP 敏感的业务固定走主 WAN；下载、普通浏览继续双线负载。出口不是「越均衡越好」，关键业务需要确定性。
  2. 会话保持：开启源 IP 粘滞，同一客户端的新连接优先走同一出口；配合较长的 keepalive，减少不必要的重建。
  3. 切换迟滞：健康检查改为「连续多次失败才判定故障、恢复后稳定一段时间才回切」，避免 1% 丢包把整条链路判死；探测间隔与失败次数按线路质量调，不要照搬默认值。
  4. HA 场景补会话同步：如果出口是双机主备，必须同步会话表（conntrackd 或厂商状态同步），否则主备切换同样会断所有连接。
  5. 监控：把出口切换事件、每条 WAN 的会话数与新建速率、关键业务断连率纳入监控；链路状态翻转要能报警，而不是只在日志里刷。
  6. 验证：用丢包注入和拔纤模拟链路抖动，观察会议与远程桌面是否中断；实测切换时间控制在两秒内，关键业务源 IP 保持稳定。

根因分析

双 WAN 负载均衡的粒度是「连接」，不是「应用会话」。同一条 TCP/UDP 连接在生命周期内固定走一条出口，但新连接会被哈希重新分配；链路故障或抖动时，后续连接整体迁移，客户端出口 IP 随之改变。

NAT 是有状态的：会话表把内网地址与某个公网出口绑定，出口一变，旧映射就失效。对普通网页影响不大——重连一次就好；对长连接和源 IP 敏感的业务，就是可见的断线。

健康检查过于敏感是放大器。1% 到 2% 的丢包在高峰期很常见，连续三次探测失败就切换，等于把偶发抖动放大成频繁的会话迁移。再加上没有会话保持，源 IP 在两条线之间反复跳，问题就从「偶发」变成了「每天都在发生」。

预防措施

  • 出口架构按业务分级：先定「哪些业务必须稳定、哪些可以均衡」，再设计策略路由与会话保持；不要默认所有流量都参与负载均衡。
  • 会话保持与迟滞基线：源 IP 粘滞、健康检查失败/恢复阈值写进配置基线，新建设备不得使用「一秒三次」这类激进默认值。
  • 切换演练：每季度做一次拔纤、丢包注入演练，验证关键业务在切换中的表现，并记录恢复时间。
  • HA 会话同步：双机出口必须验证会话同步状态，主备切换演练纳入日常。
  • 监控与变更联动：出口切换、链路翻转、关键业务断连率做成看板；调整负载均衡或健康检查参数走变更评审。
  • 知识沉淀：把「负载均衡只管连接、不管会话」写进网络设计文档，避免下次扩容 WAN 时重复踩坑。

总结

双 WAN 买到的是带宽冗余和故障备份，不是「让所有连接都稳如泰山」。连接可以分摊，会话不会自动迁移；出口一变，源 IP 就变，长连接该断还是断。

真正要做的，是把「哪些业务必须固定出口」想清楚，再用会话保持、切换迟滞和监控把不确定性收住。带宽叠加是果，业务连续才是因。
