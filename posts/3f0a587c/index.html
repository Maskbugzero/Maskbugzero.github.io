Full GC 频发：接口 P99 为何周期性飙升？

本地缓存无上限、key 带版本号只增不减，老年代长期占满触发频繁 Full GC，接口 P99 周期性飙升；换有界缓存并调小堆后恢复。

问题背景

支付网关是一个 Java 服务，JDK 11、G1 垃圾回收器，启动参数 -Xmx8g，日均请求量几百万。平时接口 P99 在 80ms 左右，运行大半年没出过大事。

服务的配置读取走两级缓存：本地一个 static ConcurrentHashMap 存商户配置，Redis 做共享缓存。本地缓存是为了省掉每次请求的 Redis 往返，写入逻辑是「按商户号加配置版本号拼 key，读到新配置就写一条」。这个设计在业务只有几千商户时很舒服，几乎零开销。

故障现象

大约一个月前开始，监控上出现规律性尖刺：每天上午十点、下午三点附近，接口 P99 从 80ms 飙到 2 到 5 秒，持续一两分钟，然后又恢复正常。尖刺出现时，服务没有重启、线程池没满、数据库慢查询为零、下游接口 RT 正常。

用户侧的体感是「偶尔点一下没反应，刷新又好了」。因为持续时间短、频率不高，一开始被当成偶发抖动；直到某次和支付渠道对账时发现「请求超时但实际成功」的订单变多，才被当成正式问题排查。运维一度怀疑是定时任务整点跑批带来的周期性压力，但核对调度平台后，十点和三点都没有对应任务。

排查过程

第一步看 APM：尖刺时段所有接口同时变慢，包括纯内存逻辑的健康检查接口，说明问题不在某个下游依赖，而在进程本身。排除数据库、Redis、下游 HTTP。

第二步看 JVM。先执行 jstat -gcutil，发现老年代使用率在 85% 到 95% 之间高位震荡，Full GC 次数呈现明显的周期聚集；再开 GC 日志（-Xlog:gc*），确认 Full GC 每 20 到 30 分钟触发一次，单次 STW 3 到 5 秒，和 P99 尖刺完全对齐。

第三步定位对象。jcmd GC.class_histogram 加一次堆转储分析，占用最多的是 ConcurrentHashMap$Node，关联到商户配置对象，总量约 120 万个条目、占用 4.5GB。而线上活跃商户只有三万个左右——平均每个商户在缓存里留了四十份配置。

第四步回到代码。本地缓存的 key 是「商户号 + 配置版本号」，每次配置变更都会写入新 key，旧 key 从不删除；static Map 没有任何容量上限和过期策略。业务接入的商户越来越多、配置变更越来越频繁，缓存只增不减，老年代被长期存活对象填满。

第五步确认回收行为：这些对象都被静态 Map 强引用，G1 判定为存活对象，Full GC 收不掉；堆又设到了 8G，一次 Full GC 的标记与回收时间随堆大小线性增长，于是出现「收不掉但反复触发」的锯齿。堆越大，单次停顿越长，也就解释了为什么尖刺能到 5 秒。

解决方案

  1. 把无界缓存改成有界缓存：本地缓存换 Caffeine，设置 maximumSize 和 expireAfterWrite；key 规范为纯商户号，配置变更走「覆盖写 + 主动失效」，不再用版本号堆新 key。
  2. 调整堆与回收参数：对象活跃集实测约 2.5GB，把 -Xmx 从 8G 降到 4G，减少单次 Full GC 的扫描与回收时间；G1 设置 MaxGCPauseMillis=200，并保留 -XX:+HeapDumpOnOutOfMemoryError。
  3. 补齐可观测性：开启 GC 日志滚动归档，把 GC 次数、单次停顿、老年代使用率、缓存条目数纳入监控；P99 曲线与 GC 停顿做同图关联，避免下次再看错方向。
  4. 代码评审红线：静态 Map 作为缓存必须在评审时说明容量与过期策略，禁止「只写不删」的本地缓存进入主干。
  5. 验证：压测两小时，Full GC 零次，P99 稳定在 80ms；上线后观察一周，十点、三点的尖刺消失，缓存条目数稳定在三万上下。

根因分析

Full GC 的直接触发条件是老年代空间不足，而这次老年代被「逻辑上早已过期、但引用上仍然存活」的缓存对象填满了。静态 Map 强引用着所有历史版本配置，垃圾回收器无法判断它们已经没用，只能当作存活对象反复扫描。

第二层原因是堆设置与实际活跃集不匹配。8G 堆在活跃集只有 2.5G 的场景里，不但没有收益，还让每次 Full GC 的停顿时间变长——堆越大，标记和回收要扫的内存越多。很多人习惯「堆越大越安全」，但停顿时间恰恰和堆大小正相关。

第三层是监控盲区：团队一直盯着接口 P99、错误率、下游 RT，却没有看 JVM 内部的 GC 状态。P99 尖刺被当成网络抖动查了很久，直到打开 GC 日志才把因果对上。

预防措施

  • 缓存必须有界：本地缓存统一使用成熟组件并配置容量、过期时间与淘汰策略；禁止裸 static Map 长期持有业务对象。
  • JVM 参数基线：堆大小按实测活跃集设定（一般 1.5 到 2 倍），不是越大越好；GC 日志常开并滚动归档，保留至少两周。
  • GC 纳入 SLO：把「单次 GC 停顿」和「每分钟 GC 次数」做成告警指标，例如单次停顿超过 500ms 或 Full GC 每小时超过一次即告警。
  • 容量与压测：新业务接入、配置模型变更时评估缓存条目增长曲线，压测覆盖长时间运行场景，而不是只压峰值 QPS。
  • 堆转储能力：预置 jcmd、MAT 分析环境，故障时能快速拿到对象分布，而不是靠猜。
  • 代码评审清单：把「缓存容量、过期、key 设计」列为 Java 服务评审的固定检查项。

总结

Full GC 不是「JVM 的脾气」，而是对象生命周期管理的账单。静态 Map 只写不删，等于把每一份历史配置都钉在内存里；堆设得再大，也只会让每次停顿更长。

排查这类问题，接口指标只能告诉你「慢」，GC 日志和对象直方图才能告诉你「为什么慢」。把 JVM 内部状态纳入日常监控，P99 的锯齿就不会再被误判成网络抖动。
