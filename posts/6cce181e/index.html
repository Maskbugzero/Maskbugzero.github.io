问题背景

两个月内，同一类故障发生了两次。9 月 1 日凌晨，堡垒机根分区写满：journalctl 卡死、systemctl 全部超时、Web 登录 502，只能靠 IPMI 进单用户模式救援。一周后的 9 月 7 日凌晨，一台刚上线一周的监控采集节点以同样的方式倒下，还连带 3 台 PVS 服务器的日志上报中断。

两台机器系统不同（Rocky 9.4 与 Debian 12），部署时间和用途都不同，但 journald 都是默认配置，也都「从没出过事」。触发源不同——一个是服务崩溃循环，一个是外部扫描流量——结局却完全一样：日志把根分区吃光。

故障现象

两台机器的表象高度一致：

  • 根分区 100%：A 机 48G/48G，B 机 8 分钟内从 12GB 可用直接归零。
  • journalctl 卡死或刷屏：A 机执行任何 journalctl 命令无响应；B 机 journalctl -f 每秒输出 200 行以上。
  • systemctl 全部超时，服务因 No space left on device 相继失败；B 机一度进入只读模式。
  • A 机堡垒机 Web 登录 502；B 机连带 200 多台无盘终端的性能数据采集中断。
  • 都只影响本机，排除共享存储与全局变更。

差异在日志来源：A 机是自研 Agent 崩溃循环，每秒数百行 traceback；B 机是外部扫描流量，日志以 kernel: UFW BLOCK 和 sshd: Failed password 为主。

排查过程

共同点：journal 目录独占根分区

du -sh /var/log/journal/* 显示 48G 与 47G。这里要先弄清 journald 的三个语义：

  1. Storage=auto 只看 /var/log/journal 目录是否存在——存在即持久化，与剩余空间无关，磁盘被日志吃光也不会退回内存。
  2. SystemMaxUse/SystemKeepFree 为空时按「所在文件系统 10%/15%」计算上限，但活跃文件的写入速度远快于回收速度。
  3. 单文件没有 MaxFileSec 约束，A 机的 system.journal 单文件涨到 48G。

场景一（A 机）：服务崩溃循环

systemctl status 显示自研 Agent 处于 start-limit-hit，触发源是白名单收口后审计转发接口 403。服务配置是致命组合：Restart=always + RestartSec=1 + StartLimitBurst=100/60s，约每秒 1.7 次重启；Python 服务每次启动失败输出数十行 traceback 与 systemd 事件，折算每秒数百行日志持续灌入。

这里有一个语义陷阱：把 Restart=always 改成 on-failure 并不能止血——exit 1 属于非干净退出，照样会重启。真正有效的是把 RestartSec 拉到 10 秒以上、把 StartLimitBurst/IntervalSec 收紧到「5 分钟 5 次」，让服务在触发 start-limit 后进入 failed 终态而不再刷屏。定位风暴起点也很关键：journalctl --list-boots 与 systemctl status 的时间戳对齐后，确认刷屏从白名单收口当晚 23:50 开始——把「什么时候开始」钉死，才能回溯到「当晚改了什么」，而不是泛泛地怀疑系统。

场景二（B 机）：外部扫描流量

journalctl 按进程统计一小时日志来源：124 万条 kernel: UFW BLOCK、31 万条 sshd: Failed password。默认 RateLimitBurst=10000 / RateLimitIntervalSec=30s 在每秒 200 行的持续刷写下形同虚设——计数器 30 秒才重置一次，30 秒内产生的日志早已远超上限；触发的 Suppressed X messages 只丢弃部分消息，剩下的照样落盘。iostat 显示 await 从 12ms 飙到 380ms，写入速度超过磁盘能力。

复现验证

用 logger 以每秒 300 行灌日志，30 秒写入 1.2GB，确认瓶颈是「日志产生速度远超磁盘 I/O 与回收速度」，两台机器的机制完全一致。

解决方案

紧急止血

  1. 停掉刷屏来源：A 机 systemctl stop fortress-agent；B 机用 drop-in 临时收紧限速（RateLimitIntervalSec=10s、RateLimitBurst=2000）。
  2. journalctl --vacuum-time=2d 回收历史日志，systemctl restart systemd-journald。
  3. B 机 3 分钟内根分区从 100% 回落到 71%，服务逐步恢复。

服务侧

  • 重启策略基线：Restart=on-failure + RestartSec≥10 + StartLimitBurst=5/300s；退出码规范化，非致命错误返回 0。
  • 日志聚合前置：UFW、sshd、kernel 这类高频日志交给 rsyslog/fluent-bit 送日志服务器，journald 只留关键事件；主机侧启用 fail2ban 从源头减少无效日志。

监控与验证

  • 根分区可用空间低于 15%–20% 告警；journalctl --disk-usage 与 RateLimit 触发计数纳入监控。
  • 模拟每秒 300 行写入，确认限速生效、根分区不再增长；两台机器连续 30 天零复发。

根因分析

直接根因是 journald 默认配置在两类高频写入场景下都不设防：RateLimit 默认值过宽、SystemMaxUse/SystemKeepFree 为空依赖比例默认、单文件无轮转约束；叠加各自的应用层缺陷——A 机 Restart=always + RestartSec=1 的崩溃循环、B 机扫描流量未聚合未限流——日志产生速度超过磁盘回收速度，根分区被写满后连锁触发服务失败。

更深一层，是默认值被当成了基线。journald 的默认配置面向「安静的单机」，面向的是不折腾的开发机；生产服务器上任何「每秒数百行」的来源——无论是失控的崩溃循环还是公网的扫描流量——都会把这套默认值击穿。另外，Storage=auto 的判定只看目录存在性，磁盘写满也不会自我保护，这些语义不弄清楚，排障就会在「为什么自动清理没生效」上打转。还有一层值得记住：两台机器都是上线不久的新节点，一台是堡垒机收口的配套 Agent，一台是新建的监控采集节点。它们的共同点不是「年久失修」，而是「新上线的默认配置加上新引入的日志来源」——上线前没有任何一道门禁问过一句：这台机器最坏的日志产生速率是多少、根分区撑不撑得住？

预防措施

  • 全部服务器以 drop-in 显式下发 journald 基线：SystemMaxUse、RateLimit、MaxFileSec、MaxRetentionSec，禁止裸默认上线。
  • 服务重启策略基线化：Restart=on-failure + RestartSec≥10 + StartLimitBurst=5/300s，退出码规范化纳入代码规范。
  • 日志聚合前置：高频来源送日志服务器，主机启用 fail2ban；/var/log/journal 评估独立挂载，避免日志拖垮根分区。
  • 监控双指标：根分区可用空间与日志增长/限速触发速率，任一异常即告警。
  • 变更验收加「journald 配置 review」与日志风暴演练：模拟高频写入，验证限速与配额真实生效。

总结

两个场景、两台机器、两种触发，最终都落在同一套默认配置上：RateLimit 过宽、上限为空、单文件不轮转。崩溃循环和扫描流量只是两种「怎么灌水」的方式，真正的问题是桶没有盖。journald 的默认值面向安静的单机，而生产环境的日志来源从来不会安静——把限速、配额、轮转显式写下来，把高频日志送走，把增长速率监控起来，才是让根分区不再被日志淹掉的完整答案。
