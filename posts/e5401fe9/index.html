maxUnavailable 100%：发版时服务归零

发版策略改成 maxUnavailable 100% + maxSurge 0，上线先删光 Pod 再重建，发版窗口 5xx 一分多钟；改回 maxUnavailable 0 后恢复。

问题背景

订单服务跑在 Kubernetes 上，Deployment 10 个副本，滚动更新参数一直是默认的 maxSurge: 25%、maxUnavailable: 25%。按这个配置，一次发版大约三分钟，期间最多两个副本不可用，用户基本无感。

后来有同事嫌发版慢，把参数改成了 maxSurge: 0、maxUnavailable: 100%：先一次性停掉所有旧 Pod，再一次性拉起所有新 Pod，发版时间从三分钟缩到四十秒。这个改动在测试环境跑了几次，没发现问题，就随着一次普通提交进了主干。

故障现象

生产发版窗口在下班后，第一次用新策略上线，监控立刻告警：接口 5xx 比例在几十秒内冲到 100%，持续一分多钟才回落。用户侧表现为页面打不开、App 请求报错；但发版本身「成功」——kubectl rollout status 显示完成，Pod 也全部 Running。

查服务端点的数量曲线，问题一目了然：发版开始后，Endpoints 从 10 个直接掉到 0，过了大约七十秒才开始回升，最后回到 10。也就是说，在那七十秒里，这个服务在集群里是「不存在」的。

更早的几次发版其实也有苗头：发版时段错误率偶尔冒个小尖，但流量低、没人注意；这次正好赶上另一个业务在做批量调用，把窗口放大成了事故。当时值班同时在处理另一个告警，第一反应是流量突增，直到把发版记录和错误曲线叠在一起，才确认两条线是同一件事。

排查过程

第一步对齐时间线：5xx 曲线的起点和 Deployment 的更新时间完全重合，范围只在这一个服务，排除依赖故障和节点问题。

第二步看滚动过程：kubectl get pods 显示旧 ReplicaSet 被一次性缩到 0，新 ReplicaSet 从 0 扩到 10；Pod 事件里能看到调度、拉镜像、容器创建、就绪探针通过，整个链路大约七十秒。这段时间里旧 Pod 已经全没了，新 Pod 还没就绪，Endpoints 自然是 0。

第三步查配置：kubectl get deployment order-api -o yaml 里写着 maxSurge: 0、maxUnavailable: 100%。到这一步根因明确——不是探针配错，不是调度失败，也不是 HPA 把副本缩了，而是发版策略本身允许「全部副本同时不可用」。

第四步做对照实验：在预发环境用同样配置发版，同时压测接口，5xx 比例 100%，持续约 70 秒；把 maxUnavailable 改成 0、maxSurge 改成 1 后重新发版，压测零错误，Endpoints 始终保持在 10 个以上。

第五步复盘变更来源：git 历史显示参数是在一次「加速发版」的提交里改的，评审时大家只看了流水线耗时，没有人检查可用性影响；测试环境流量低，也没有发版期间的压测用例。

解决方案

  1. 改回保护性参数：maxUnavailable: 0、maxSurge: 1（或按副本比例设 25%）。更新期间先建新 Pod，就绪后再删旧 Pod，容量不减。
  2. 就绪探针兜底：readiness 探针要能真实反映「可以接流量」，包括依赖连接、缓存预热；新 Pod 未就绪前不进 Endpoints。
  3. 加策略校验：在 CI 里对 Deployment 清单做断言，禁止 maxUnavailable: 100%、禁止 maxSurge: 0 与 maxUnavailable 大于 0 同时出现；也可以用 Kyverno/OPA 在集群侧拦截。
  4. 发布期压测：流水线里加一条「发版期间持续打流量」的冒烟任务，错误率超过阈值就自动暂停 rollout（kubectl rollout pause）。
  5. 灰度发布：重要服务改用金丝雀或 Argo Rollouts，先放 10% 流量观察，再全量。
  6. 验证：连续三次发版，压测零 5xx，Endpoints 数量最低保持 90% 以上，发版耗时回到两分半左右——比四十秒慢，但这是可用性的价格。

根因分析

maxUnavailable 的语义是「更新期间允许不可用的副本数上限」，maxSurge 是「允许临时超出期望副本数的上限」。两者共同决定滚动更新的节奏：控制器只会遵守你给的约束，不会替你保证可用性。

把 maxUnavailable 设成 100%，等于告诉控制器「全部副本都可以先停掉」；再配合 maxSurge: 0，控制器没有创建新 Pod 的空间，只能先缩容再扩容。于是「滚动更新」退化成「停机重建」，只是它的名字还叫滚动更新。

这个改动之所以能进生产，有三个原因：一是把「发版速度」当成唯一指标，忽略了可用性成本；二是测试环境流量低、没有发版期压测，问题被掩盖；三是评审只看了流水线耗时，没有人对着 Deployment 策略问一句「最坏情况会怎样」。顺带说一句，PDB 保护的是节点排空这类驱逐场景，不覆盖 Deployment 的正常滚动更新，不能拿它当这道防线的替代品。

预防措施

  • 策略基线：无状态服务统一 maxUnavailable: 0、maxSurge: 1~25%；任何偏离基线的配置必须在变更单里写明理由与回滚方案。
  • CI 拦截：在清单校验阶段拒绝危险组合（100% 不可用、Surge 为 0 且 Unavailable 大于 0），让错误配置根本进不了集群。
  • 发版期压测：把「持续流量 + 错误率阈值 + 自动暂停」做进发布流水线，而不是只验证 Pod 起没起来。
  • 监控补齐：把 Endpoints 数量、发版期间 5xx、Pod 就绪耗时纳入发版看板；发版事件和监控曲线自动关联，让「副本数、端点数、错误率」三条线在同一张图上，任何人一眼能看出容量是否掉零。
  • 发布演练：每季度做一次「发版期故障」演练，验证暂停、回滚、灰度三条路径都可用。
  • 变更文化：性能优化不能只看单项耗时，要把可用性、恢复时间一起纳入评审。

总结

Kubernetes 不会阻止你把服务配成「发版即停机」，它只会忠实地执行你的策略。滚动更新之所以叫滚动，是因为参数约束了「至少留多少可用」；把这个约束拿掉，剩下的就只是更新，没有滚动。

发版速度是体验，可用性是底线。任何以底线换体验的改动，都值得在评审时多问一句：最坏情况下，用户会看到什么？
